# 章节写作：从任务走到机制

## 整本书如何推进

先确定一条能力主线，例如“从单次请求处理，走到有状态、可观测、能恢复的服务”。目录中的每章应解决前一阶段显露出的限制，并说明读者已有的知识。不要把产品功能清单直接改成目录。

用一个小而完整的系统建立共同术语。后续章节尽量复用已有对象与输入，只有新的机制要求新场景时才切换。给不同基础的读者说明阅读路径：首次阅读先看主流程，工程细节放在相关机制之后或独立小节中。

章间连接说明“上一章解决了什么，还留下什么问题”。正文不反复复制环境安装和全书背景，跨章依赖用链接承接。

## 一节内容的推进方式

以下是思考顺序，不是每节都要照搬的小标题：

1. 给出可辨认的任务或故障。例如同一查询第二次返回旧值，比“缓存非常重要”更容易引出问题。
2. 定义解决问题需要的对象，明确边界。类比可用于首次理解，随即映射到实际字段、接口或组件；说明映射不到的部分。
3. 用最小代码或数据结构表达机制。去掉与本节无关的适配、UI 和批量调度，但保留决定行为的判断、状态更新与终止条件。
4. 沿具体输入走一遍。显示关键调用、输入输出、状态变化及最终结果；必要时再走一次失败或边界路径。
5. 解释设计取舍：省了什么，新增什么代价，在何种条件下不合适。
6. 安排一个能检验本节判断的实验，或给出已有实验的分析。

对于以定义为主的小节，可省去完整实验；对于核心机制，不要只有定义与优缺点表。

## 代码附近应该写什么

代码前交代输入、目标及被省略的细节。代码后直接解释决定行为的语句：修改了哪个对象，为什么在这里修改，不这样做会导致什么。对象首次出现时说明存活范围与归属，例如请求局部变量、跨轮会话状态或持久化数据。

对循环重点解释：这一轮看到的信息、动作如何产生、结果如何进入下一轮、正常结束与耗尽预算的区别。对并发或分布式流程，指出实际执行方、通信数据和控制权转移。

三类代码须能一眼区分：

| 类别 | 写法 | 读者预期 |
| --- | --- | --- |
| 机制伪代码 | 标注伪代码与省略项 | 建立模型，不直接执行 |
| 源码摘录 | 给出真实路径、符号与必要上下文 | 回到实现定位与阅读 |
| 完整实验 | 提供文件、依赖、运行命令与验收办法 | 可以在说明的环境运行 |

不要给带省略号、虚构 API 或缺失函数的片段加上“一键运行”。若展示 Python 风格伪代码，不让读者误以为某个 SDK 真有该接口。

## 图、表与数学表达

图用来表达边界、结构或顺序，正文解释读图方向和重要边。图中组件名与代码保持一致。多步状态变化宜用时序图或轨迹表；具有并列比较维度时才用表格。

先说明数学式中的量、单位和适用条件，再代入具体输入。估算、理论上限与测量结果分开。对性能比较保留输入规模、硬件、并发和计时范围，不只写一个倍数。

Markdown、HTML、PDF 沿用用户要求和项目已有构建方式，不因参考网站使用 Astro 就引入 Astro。在线页面按 [web-reading.md](web-reading.md) 处理布局、视觉与阅读交互；HTML 中代码须保留空白和可读缩进，复制功能存在时应复制原始代码；视觉验收与结构检查分别报告。

## 实验如何嵌入正文

在读者已经知道“要观察什么”之后插入实验卡。卡片可以很短，但应包含：问题、任务、观察点、成功条件和实现链接。编号沿用现有章节体系；难度描述以所需前置知识和工作量为依据，不机械复制星级。

实验之后解释结果与机制的联系。例如“第二轮未发起读取，因为第一次得到的值仍在缓存中”，比“性能显著提升”提供更多信息。

章末归纳本章建立的边界和设计判断。思考题让读者预测一个变化的影响、定位一条错误轨迹，或提出可检验的改进；避免只要求背术语。

## 语气

采用技术书的解释口吻，保持可理解的因果连接。重要术语首次出现时给中文解释，必要时保留英文。具体场景和类比服务于机制，不能代替机制。

少用“赋能”“革命性”“显而易见”。没有证据时不声称某方案更好。也不用固定的对立句、三点清单、加粗口号或结尾金句制造节奏。标题应说明当前要解决的问题。
