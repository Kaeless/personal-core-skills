# 实验与教学代码

## 先写出要检验的判断

用一句话描述实验问题，例如“丢弃旧工具结果是否导致重复请求”。列清基线、变化条件、保持不变的输入和预算、观察信号及成功条件。比较多个机制时，先给一个能理解的基线，再逐个增加变化。

防止把实验设计成必然支持结论的演示。消融某项信息时，不要额外加入提示来告诉系统“这项信息被移除了”；若协议强制保留空字段，记录这个限制。不要同时换模型、提示词与任务后将差异归因于单一因素。

小型教学实验以解释机制为主；若要主张普遍效果，增加适当的配对任务、重复次数和不确定性分析。不要给所有实验强加复杂统计，也不要把一次成功外推成可靠性结论。

## README 的阅读路径

README 应回答下列问题，标题和顺序按项目调整：

- 正文哪一节对应这个实验？读者需要理解哪个问题？
- 为什么采用这些方法，具体比较什么？
- 从哪个目录运行，依赖什么版本、数据、硬件或凭据？
- 最短路径如何启动一次小实验，应该先看哪条输出？
- 怎样读取轨迹和结果，什么现象支持或反驳假设？
- 从哪个入口阅读源码，如何改变一个条件继续探索？
- 失败时先检查哪一步，相关参考资料在哪里？

每条关键命令附近说明目的和产物。安装、配置、运行与结果解释不要隔着大段无关介绍。公共环境可集中维护，单实验仍需给出明确跳转与工作目录。

标明交付状态：本地可运行实验、依赖外部仓库的复现指南、尚未实现的设计方案。使用外部代码时固定可核对的版本，说明哪些步骤由本项目实现。

## 代码形态

优先让读者能从入口连续读到核心机制。小实验可以单文件；代码增长后再按职责拆分。以下是可选角色，不是必须生成的目录清单：

| 角色 | 常见文件 | 责任 |
| --- | --- | --- |
| 人可操作的入口 | `main.py`、`demo.py` | 参数解析、单次任务、结果位置 |
| 核心机制 | `agent.py`、`retriever.py`、`pipeline.py` | 循环、策略、状态与数据流 |
| 外部能力 | `tools.py`、`client.py` | I/O 和服务协议适配 |
| 配置 | `config.py`、`env.example` | 默认值、环境覆盖与合法性检查 |
| 对照运行 | `experiment.py`、`evaluate.py` | 相同输入下运行各条件并记录结果 |
| 验证 | `tests/` 或 `test_*.py` | 关键行为、边界与失败结果 |

按目标仓库语言与规范编码。Python 新实验通常使用 `snake_case` 函数、`PascalCase` 类型、常量大写，以及关键接口的类型标注。简单记录用字典即可；字段有稳定约束时再选 dataclass 等结构。不为一个循环引入插件系统或多层继承。

注释和 docstring 说明教学目的、输入输出约束、状态为何如此更新、边界为何如此处理。中文讲解优先，标识符保持语言惯例；不在每条普通赋值后重复中文翻译。

让核心机制直接可见。批量调度、供应商兼容、终端渲染不要挤进核心算法。能独立计算的评分和聚合逻辑与外部运行环境分离，便于离线验证。

## 离线与在线

离线路径适合展示执行流程或验证本地算法，只有它能帮助理解时才提供。明确它使用固定响应、规则策略、真实本地计算还是保存的历史轨迹。

在线模式缺少凭据或服务不可达时，输出明确失败；不要悄悄切成 mock 再报告真实服务成功。如果允许显式回退，在结果中记录实际模式、供应商、模型和回退原因。依赖安装需要网络时，也要说明“离线运行”不等于“离线安装”。

配置样例只放变量名和非敏感默认值。日志避免保存凭据。为真实调用设置适当的超时、轮数或预算；重试应保留失败证据。SDK 兼容细节依据当前官方资料核对，不把原书某个模型的特殊处理推广到全部模型。

## 输出应支持解释

终端先展示一条可读轨迹，再给摘要；需要复盘时保存 JSON 或 JSONL。对 Agent 记录可获得的消息、工具参数、观察和动作，不伪造或要求供应商未公开的内部思维过程。其他系统记录对应的输入、分支、状态变化及结果。

较完整的对照运行可记录：任务 ID、条件、模式、版本、配置、种子（若适用）、耗时、调用次数、资源消耗、终止原因、判定与证据路径。小实验选择足够解释结果的字段，不机械填满 schema。不存在的消耗信息用未知值，不能以零假装测量过。

分别记录运行错误与任务失败。统计时公开分母、排除项和缺失配对；不能静默删去失败后只比较成功样本。服务错误若消耗了预算，也应计入相关成本。

## 验证与分析

至少检查 README 最短命令和一个与核心判断相关的边界。涉及复杂外部环境时，先测试可独立运行的本地逻辑，再报告实际完成的在线验证层级。纯写作任务无需搭建用户没要求的完整服务。

测试应回答实际问题，例如：预算耗尽是否停止；空结果是否被当成成功；损坏的响应是否被记录；两条配对轨迹是否对应同一任务。避免仅断言文档标题存在或输出恰好等于实现中的常量。

分析失败时找最早偏离依据的步骤，再沿因果链解释后续结果。检查观察是否缺失、数据是否错误、状态是否未更新、验证器是否漏检。成功终态也可能包含过程问题，两者分别说明。

最终列出已执行命令及其范围，并说明仍需什么条件才能完成其余验证。结论来自结果，允许推翻原来的预期。
